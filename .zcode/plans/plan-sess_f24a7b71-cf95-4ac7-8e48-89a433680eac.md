## Ключевые находки исследования (лягут в основу плана)
Проверено по коду (не только по роадмапу):
1. **Структура:** 2 Gradle-модуля (`java-metrics-lib` = core+javaparser пакеты, `java-metrics-cli`). God-class `JavaParserJavaMetricsAnalyzer` (1277 строк), 35 визиторов регистрируются явно (`buildClassVisitors`/`buildMethodVisitors` + 2 инлайн).
2. **Silent failures:** 15 из 35 визиторов (~44 сайта) с `catch (Exception ignored)` вокруг `.resolve()`; плюс `tryResolve` в анализаторе и `System.err` в `JavaParserTypeSolverFactory`. Пайплайн диагностики уже есть (`AnalysisDiagnostic` → `MetricReport.diagnostics` → JSON), но визиторы к нему не подключены — это готовая точка интеграции.
3. **Память:** все CompilationUnit живут одновременно в 3 структурах до конца `analyze()` (список parsedUnits, `EnhancedJavaParserContext`, `MemoryTypeSolver`). `AnalyzedClass`+`DependencySnapshot` уже частично готовы как «слепки» (MOOD и пакетные метрики уже считаются без AST); NOC/FDP пока требуют AST.
4. **Дефекты вне роадмапа (регистрируем в tech-debt-tracker):** (а) race condition — stateful Halstead-визиторы шарятся между потоками parallelStream; (б) ForkJoinPool создаются на каждый `analyze()` и не закрываются; (в) директории в `--classpath` молча отбрасываются; (г) правило `HAS_METHOD_RULE` в `class-level-rules.json` мертво (у `Condition` нет поля `value`).
5. **Сериализация:** 3 независимых пути (MetricReportJsonWriter, DetectResultWriter, ValidateCommand), Jackson только в CLI; shadowJar `minimize()` — риск для рефлексивного Jackson.
6. **Тесты:** snapshot-тестов JSON нет; `PerformanceBenchmarkTest` с hardcoded путём и без assertions — нужен baseline до рефакторинга памяти.

## Нарезка задач

**Stage 0 — Safety net (новая, обязательная до рефакторингов):**
- **TASK-001** Golden-тесты JSON-контракта analyze/validate/detect (синтетический тестовый проект, зафиксированные эталонные выходы) — защита от breaking changes в Фазах 2–4.
- **TASK-002** Параметризация PerformanceBenchmarkTest + замер peak heap + фиксация baseline-цифр в implementation-plan.md (критерий Фазы 2: −30%).

**Фаза 1 — Reliability (роадмап 1.1, 1.2):**
- **TASK-101** Диагностический канал: `AnalysisCollector` (реализует `Consumer<MetricResult>` + `warn()`), замена дженерика базовых классов визиторов, потокобезопасная доставка в `MetricReport`.
- **TASK-102** 12 resolving class-визиторов (CBO, ATFD, RFC, LCOM, NOA, DAC, LAA, MPC, DIT, SIZE2, NOC, FDP): silent catch → `UNRESOLVED_SYMBOL`/`UNRESOLVED_TYPE` (WARNING) с дедупликацией и лимитом на класс.
- **TASK-103** Method-визиторы (CDISP, CINT, NOAV) + `tryResolve` анализатора + ошибки `JavaParserTypeSolverFactory` → диагностика.
- **TASK-104** `resolutionCoverage` в ProjectReport + JSON (backwards-compatible) + docs/RUN.md.
- **TASK-105** TypeSolver: поддержка директорий classpath, module-info.java, fallback-политика ReflectionTypeSolver.

**Фаза 2 — Performance (роадмап 2.1, 2.2 + hotfix-находки):**
- **TASK-201** Thread-safety hotfixes: Halstead-визиторы stateless, жизненный цикл ForkJoinPool (закрытие в finally), удаление мёртвого `compilationUnitsByClass`.
- **TASK-202** Обогащение DependencySnapshot: NOC из `directSuperTypes`, FDP из новых полей снимка — кросс-классовые метрики без AST (ADR).
- **TASK-203** `AstMemoryManager`: per-class окно анализа, освобождение CU после снятия снимка, замена AST-backing MemoryTypeSolver (ADR).
- **TASK-204** Двухпроходный пайплайн: локальные метрики при парсинге → release AST → глобальные из снимков; memory gate −30% vs baseline TASK-002 (золотые тесты TASK-001 зеленые).
- **TASK-205** Конкурентность: ThreadLocal-аккумуляция + merge, критерий линейного масштабирования.

**Фаза 3 — Architecture (роадмап 3.1, 3.2):**
- **TASK-301** `MetricRegistry` + `MetricDefinition` (метаданные, привязка визиторов, фабрики для контекстных NOC/FDP); агрегации остаются в анализаторе (ADR). Критерий: добавление метрики = 1 класс + 1 запись.
- **TASK-302** Джексон-сериализация: mixins, консолидация 3 путей записи, проверка shadowJar minimize(); контракт TASK-001 зеленый.

**Фаза 4 — Ecosystem (роадмап 4.1, 4.2):**
- **TASK-401** SARIF 2.1.0 writer + флаг `--format json|sarif` (validate/detect; analyze — опционально).
- **TASK-402** Унификация конфигов (JSON+YAML везде, обратная совместимость) + починка мёртвого `HAS_METHOD_RULE`.

## Зависимости
001 → (102, 203, 302); 002 → 204; 101 → 102 → 103; 202 → 203 → 204; 301 после 104. Stage 0 — перед всеми рефакторингами. Quick wins (HAS_METHOD_RULE из 402, Halstead из 201) можно вытянуть вперёд.
