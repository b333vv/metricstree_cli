## Implementation sequence

1. Reject malformed gate mappings, unknown nested gate keys, wrong list element types, empty/unknown failOn values, unknown growth metrics, and negative/nonfinite budgets; retain the existing top-level unknown-key warning policy for compatibility.
2. Introduce a small immutable GateSettings value held by ProjectConfig rather than adding more positional gate fields. Update existing callers/tests with named factory helpers. Initially carry existing growth/failOn plus nullable mode/policy/enforcement/analysis settings; new options become active in their owning tasks.
3. Add real gate --profile/-p override of config.profile for legacy thresholds, with the same Profiles lookup and key-by-key inline override semantics. Explicit -t replaces profile/config thresholds. Do not add a conflicting global short option.
4. Add origin-aware validation helpers that include config path and dotted key. Reject simultaneous --config and --no-config.
5. Reserve maintainability config parsing for ML-014. When new policy is wired, an explicit gate --profile with maintainability is rejected; a top-level profile for validate is ignored by that policy.

## Implementation notes

- Commit: `ML-002: validate the gate config section and give gate a real --profile option`.
- Files changed: new `GateSettings.java`; `ProjectConfig.java`, `ProjectConfigLoader.java`,
  `GateCommand.java`, `Profiles.java`, `ProjectConfigs.java`, new `ConfigError.java`,
  `JavaMetricsCliApplication.java`; tests `ProjectConfigLoaderTest`, `GateCommandTest`.
- Behaviour:
  - The `gate:` section is validated as a whole in `ProjectConfigLoader`. Rejected, each naming the
    config file and the dotted key: a `gate:` that is not a mapping; an unknown nested key
    (`growht`); a non-mapping `growth`; a `failOn` that is not a list, contains a non-string, is
    empty, or names an unknown / non-selectable type; a `growth` key that is not a metric code; and a
    budget that is negative, non-numeric or non-finite. All of these were previously silent
    fallbacks, and the direction mattered — `failOn: "new-violation"` (a bare string) was read as
    "absent", which means *all* types fail, so the author's narrower selection became a stricter gate.
  - `GateSettings` is the immutable value `ProjectConfig` now holds instead of two positional gate
    fields. It carries `growth` and `failOn` plus nullable `mode`, `policy`, `enforcement` and
    `analysis`; those four are **parsed and validated but not yet acted on**, because ML-004, ML-007
    and ML-019 own their behaviour and a setting that exists without behaviour is a silently ignored
    setting. `null` settings means "section absent", which the flat record could not distinguish from
    "section present but empty".
  - `gate -p/--profile` is a real option now. It overrides `profile:` from a project config through
    the same `Profiles` lookup, and the config's inline `thresholds:` still merge on top (one
    statement: "use relaxed, except CBO ≤ 5"). An explicit `-t` replaces the profile table outright
    rather than merging. The option is only on `gate`; no conflicting global short option was added.
  - New `ConfigError` marks malformed configuration as a usage error, so it exits 2 with the message
    alone. It extends `IllegalArgumentException`, so existing call sites are unchanged; only the
    reporting differs. Previously `failOn: [everything]` was reported as `Analysis failed: ...` with
    exit 1, which told a CI author their change broke the tool when nothing had been analysed.
  - `--config` with `--no-config` is now an error. Silently preferring one would let a build that
    reads no config be made to look like one that read the named file.
- Tests: `ProjectConfigLoaderTest.gateConfigRejectsWrongShape` (15 cases), `gateConfigAcceptsTheDocumentedShape`,
  `absentGateSectionIsNull`; `GateCommandTest.gateProfileFlagWorks`,
  `gateProfileFlagSelectsBetweenProfileTables`, `unknownGateProfileIsAUsageError`,
  `explicitThresholdsBeatProfile`, `mutuallyExclusiveConfigOptionsExitTwo`.
  `ProjectConfigLoaderTest.explicitMissingConfigIsAnErrorNamingTheFlag` and the existing
  `unknownFailOnValueIsAUsageErrorNamingTheFile` still pass unchanged, as do the config-discovery and
  `--no-config` tests. `./gradlew check` green (179 CLI tests plus the library and integration suites).
  Verified against the installed distribution in a throwaway repository: `gate --base HEAD~1 -p strict`
  reports the crossing with strict's own bound, `-p nope` and `--config` + `--no-config` both exit 2.
- Compatibility changes (documented in `docs/RUN.md`):
  1. A `gate:` section that is malformed, misspelled or empty in `failOn` is now an error rather than a
     silent fallback. This is the intended direction — a gate that cannot check what its author asked
     for must not report success — but it can stop a build that previously ran with default settings.
  2. A malformed config now exits 2 with a clean message instead of exit 1 with `Analysis failed:`.
  3. `gate -p` is new; the GitHub Action's existing `-p` invocation previously failed as an unknown
     option. No existing invocation changes meaning.
  4. The top-level unknown-key warning policy is retained exactly as it was.
- Remaining limitations: `mode`, `policy`, `enforcement` and `analysis` are validated but inert (see
  above). The `KNOWN_METRICS` set is restated in `ProjectConfigLoader` rather than shared with
  `ConfigLoader`, because the two sections answer different questions; if `MetricCode` ever gains a
  code that is legal in thresholds but not a gate budget, one of the two needs a deliberate change.
  `ProjectConfig.effectiveThresholds()` without an argument still exists for `validate` and `detect`;
  it delegates to the new override-aware overload with no override.
