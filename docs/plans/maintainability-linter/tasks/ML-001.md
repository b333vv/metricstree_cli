## Implementation sequence

1. Read every use of Threshold.min/max and the DEBT-14 golden assertion. Add the regressions below before changing bounds.
2. Keep primitive bounds for legacy compatibility; omitted min becomes -Double.MAX_VALUE and omitted max remains Double.MAX_VALUE. Reject an empty constraint, non-number, nonfinite number, inverted range and unknown metric code in ConfigLoader with the exact key in the error.
3. Fix GateEvaluator.worsened: determine worsening by configured finite sides, not min > 0. For two-sided bounds use distance outside the interval; inside-to-inside movement has no universal bad direction and emits no generic worsening warning. Growth budgets remain explicitly directional increases.
4. Suppress sentinel bounds in human messages; retain legacy numeric JSON sentinel fields for now. New v2 uses null/absent bounds later. Do not alter metric values.
5. Review the deliberately changed zero-valued validation golden and document one-sided-threshold migration. Resolve DEBT-14 only after the test proves zero passes.

## Tests to write first

The names below describe required scenarios; use idiomatic JUnit method names. Assert outcomes
and evidence, not only completion. Documentation/manual tasks use verification checks rather than
unnecessary unit tests.

- maxOnlyAcceptsZero: CBO=0 with max=0 passes validate and gate; CBO=1 fails.
- minOnlyAcceptsLargerValue: min=2 accepts 2/3 and rejects 1; negative metric with max-only remains legal.
- rejectsInvalidThresholds: string, null, unknown code, empty object, min>max and nonfinite YAML values fail as config errors.
- maxOnlyIncreaseIsWorsening: existing above-max 2->3 is a warning when no growth budget blocks; two-sided inside 0.4->0.5 is not called deterioration.
- Existing baseline behavior still accepts unchanged violations and rejects worsening in the applicable direction.
