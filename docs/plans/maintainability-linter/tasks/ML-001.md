## Implementation sequence

1. Read every use of Threshold.min/max and the DEBT-14 golden assertion. Add the regressions below before changing bounds.
2. Keep primitive bounds for legacy compatibility; omitted min becomes -Double.MAX_VALUE and omitted max remains Double.MAX_VALUE. Reject an empty constraint, non-number, nonfinite number, inverted range and unknown metric code in ConfigLoader with the exact key in the error.
3. Fix GateEvaluator.worsened: determine worsening by configured finite sides, not min > 0. For two-sided bounds use distance outside the interval; inside-to-inside movement has no universal bad direction and emits no generic worsening warning. Growth budgets remain explicitly directional increases.
4. Suppress sentinel bounds in human messages; retain legacy numeric JSON sentinel fields for now. New v2 uses null/absent bounds later. Do not alter metric values.
5. Review the deliberately changed zero-valued validation golden and document one-sided-threshold migration. Resolve DEBT-14 only after the test proves zero passes.

## Implementation notes

- Commit: `ML-001: repair threshold bounds and the direction of "worse"`.
- Files changed: `Threshold.java`, `ConfigLoader.java`, `GateEvaluator.java`,
  `AgentMarkdownReportWriter.java`, `HtmlReportWriter.java` (sentinel suppression),
  `SarifReportWriter.java` (comment), `ConfigLoaderTest`, `GateEvaluatorTest`,
  `HtmlReportWriterTest`, `golden/validate.json`, `docs/tech-debt-tracker.md`, `docs/RUN.md`,
  `docs/PROGRESS.md`.
- Behaviour:
  - `Threshold.of(min, max)` is now the single producer of the sentinels. An omitted `min` is
    `-Double.MAX_VALUE` (was `Double.MIN_VALUE`, the smallest *positive* double), so
    `"CBO": { "max": 0 }` accepts `CBO == 0`. DEBT-14 closed.
  - `hasMin()` / `hasMax()` answer "was this side configured", and `contains` / `overshoot` /
    `describe` moved onto `Threshold` so `GateEvaluator` no longer keeps a private duplicate of the
    same three comparisons.
  - `ConfigLoader` rejects, naming the exact key: a non-object entry, an unknown metric code, an
    entry configuring neither bound, a non-numeric bound, a non-finite bound, and an inverted range.
    `asDouble()` was the trap — it turned a string into `0.0` and `.nan` into `NaN`, which fails
    every comparison. This closes the "unknown metric name is silently never matched" gap noted in
    `docs/RUN.md`.
  - `GateEvaluator.worsened` reads direction from the configured bound. Ceiling-only worsens on
    increase, floor-only on decrease, two-sided only when the value moves *outside* the interval.
    Inside-to-inside movement in a two-sided range is no longer reported as a deterioration: there is
    no universal bad direction there, and the warning was noise a reviewer had to dismiss by hand.
    Growth budgets stay explicitly directional increases.
  - Sentinel bounds are suppressed in human-facing output via `Threshold.describe()`
    ("at most 0" rather than "[-1.7976931348623157E308 .. 0]"); the legacy JSON `expectedMin` /
    `expectedMax` fields keep the numeric sentinels for compatibility (ML-020 gives v2 `null` bounds).
- Tests: `ConfigLoaderTest.maxOnlyAcceptsZero`, `minOnlyAcceptsLargerValue`, `rejectsInvalidThresholds`;
  `GateEvaluatorTest.maxOnlyIncreaseIsWorsening`, `twoSidedIntervalKeepsTheFloorDirection`. The
  existing `worsenedButWithinBoundsIsAWarning` and `floorMetricWorsensOnDecrease` were retargeted onto
  explicit max-only / min-only thresholds, because the old heuristic inferred direction from the sign
  of `min` and the new rule reads the configuration. `./gradlew check` green (165 CLI tests +
  integration tests).
- Compatibility changes (intentional, documented in `docs/RUN.md` under "One-sided thresholds"):
  1. `validate` golden: the sentinel `expectedMin` became `-1.7976931348623157E308` (8 top-level +
    7 nested occurrences) and the single `CBO == 0` check in the golden fixture flipped
    `FAILED` → `PASSED` (`passed` 25 → 26, `failed` 15 → 14). Reviewed field by field via
    `-Dgoldens.update=true`; **no metric value changed**. No other golden moved.
  2. A thresholds file that used to load with a bad bound, an inverted range or an unknown metric key
     now stops the run with a configuration error naming the key.
  3. Two-sided thresholds are unchanged numerically; the generic `worsened` warning no longer fires
     for inside-to-inside movement.
- Remaining limitations: `hasMin()` / `hasMax()` detect an omitted side by comparing against the
  sentinel, so a file that explicitly writes `-1.7976931348623157E308` as a `min` is indistinguishable
  from omitting it — harmless, since that is the same constraint, but it is why the record keeps
  primitive bounds rather than a nullable pair. Legacy JSON still serializes the sentinels; ML-020
  replaces them. NaN/Infinity metric *values* are still compared as ordinary numbers here; ML-008 makes
  them an explicit unavailable evaluation status.
