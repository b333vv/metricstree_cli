## Implementation sequence

1. Implement the three modes and default worktree exactly as the comparison table specifies. Resolve HEAD/base only once.
2. Require one merge base and retain full SHAs plus requested-ref text in ComparisonPlan. Use that SHA for both old manifest and content.
3. Build after manifests from HEAD tree, stage-0 index, or working inventory depending on mode; combine committed branch changes with local/index state for staged/worktree.
4. Detect unmerged index for staged/worktree; committed mode ignores dirty/unmerged local index because it uses only object trees. The comparison contract specifies this exception.
5. Keep planner pure relative to source writes; reject unsupported modes and missing ancestry with useful errors.

## Implementation notes

- Commit: `ML-004: resolve explicit comparison modes and one merge base`.
- Files changed: new `ComparisonMode.java`, `ComparisonPlan.java`, `ComparisonPlanner.java`; new
  `ComparisonPlannerTest.java`; `GitOps.java` gained `objectType` and `isJavaPath`.
- Behaviour:
  - **The bug this fixes.** The old gate selected files with `git diff --name-only base...HEAD`,
    where `...` made git compute a merge base internally, and then read base content with
    `git show base:path` — the *tip* of the target. For a diverged branch those are two different
    revisions, so whenever the target branch had also changed the file under review, the before
    snapshot was content the author never wrote. `advancedTargetUsesMergeBase` is the regression: it
    advances the target's tip, changes the same file there and differently on the branch, and asserts
    the plan still resolves the fork point.
  - HEAD and the requested ref are each resolved **once**; the resolved 40-char SHAs are what every
    later read uses, so the two snapshots cannot describe different points in history. The requested
    ref text is retained for error messages only.
  - Exactly one merge base is required. Zero is reported as unrelated history (with the shallow-fetch
    remedy named, because that is the usual cause and the fix is a two-second command); more than one
    is reported as a criss-cross and refused rather than resolved by git's ordering.
  - The three modes are implemented per the contract table. `ComparisonPlan` also carries
    `unsupported` (selected Java paths whose object is not a plain blob — a symlink or gitlink) and
    `untrackedIncluded`, so an unreadable input is recorded rather than dropped.
  - An unmerged index is an error in `staged` and `worktree`; `committed` never consults the index at
    all, which is what makes it ignore a dirty, conflicted checkout by construction rather than by a
    special case.
  - Local changes are computed against **HEAD**, not the merge base, so a file changed both on the
    branch and locally yields one local record rather than being re-reported as a branch change.
  - `ComparisonMode.DEFAULT` is `WORKTREE`, per the master plan's compatibility decision.
- Tests: `ComparisonPlannerTest` (11 tests) — `advancedTargetUsesMergeBase`, `modeMatrix`,
  `modeMatrixSelectsDifferentContent`, `baseHeadMeansLocalOnly`, `noMergeBaseIsAnError`,
  `multipleMergeBasesAreRejected`, `shallowMissingHistoryIsRejected`,
  `unmergedIndexIsAnErrorExceptInCommittedMode`, `unknownModeIsRejected`, `unbornHeadIsNamedAsSuch`,
  `repositoryBytesAndIndexAreUnchanged`. `modeMatrixSelectsDifferentContent` is the one that matters
  most: a file *list* that is right while the *content* is wrong is the worse failure, because the
  report looks complete, so it asserts each mode resolves the same path to a different byte string
  (committed → HEAD tree, staged → index, worktree → disk). The criss-cross and shallow fixtures were
  both verified by hand against real git before being written down. `./gradlew check` green.
- Compatibility changes: **none**. The gate still uses the old wrappers; ML-006 wires the planner in.
  `--mode` is deliberately **not** added to `GateCommand` in this task: an option that parses and is
  then ignored is exactly the "silently weaker than its author believes" failure ML-002 removed, so
  the CLI option arrives with the task that makes it do something.
- Three real bugs in my own first implementation, all found by the tests and all fixed:
  1. worktree local-change detection compared only file *existence*, so every tracked file looked
     edited and no real edit could be distinguished. Now compared against the HEAD blob's bytes —
     a file rewritten with identical content is correctly not a change.
  2. worktree mode never consulted the index, so a conflicted index was silently resolved by picking
     a stage instead of being reported. Both `staged` and `worktree` now check it.
  3. the untracked-file filter excluded paths that exist on disk, which is the opposite of the
     untracked condition, so no untracked file was ever included.
- Remaining limitations: no materialization yet (ML-005) and the gate does not consume the plan yet
  (ML-006), so the merge-base fix is not yet user-visible. Rename pairing in local state is not
  inferred for worktree mode. The planner is not wired to `gate.mode:` from a project config; that
  arrives with ML-006.
