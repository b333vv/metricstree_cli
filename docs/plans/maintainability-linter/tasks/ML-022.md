## Implementation sequence

1. Extend SARIF records to the bundled official schema for fingerprints, relatedLocations, invocations, toolExecutionNotifications and properties.
2. Map active eligible findings with stable rule IDs and URI-encoded logical paths/actual source ranges. Include configured rule metadata even when not matched.
3. Emit incomplete/evaluation diagnostics as invocation notifications; executionSuccessful is false for incomplete/error runs. A valid failed quality gate is a successful tool execution with findings.
4. Wire --format sarif for maintainability gate/detect; retain documented legacy behavior until a separate mapping is deliberately added.
5. Cross-check fingerprint/evidence/count parity with JSON; no fabricated locations for package/run diagnostics.

## Implementation notes (fill during execution)

- Commit: pending (this session)
- Tests: `FindingSarifReportTest` (8 — a quality violation keeps executionSuccessful true, an incomplete run sets it false and emits a notification, suppressed/existing/baseline debt is not re-alerted, the fingerprint and the measured range match the JSON report, a path with spaces is percent-encoded and still schema-valid, configured rules are declared even when unused, a result with no message is rejected by the official schema). Both the complete and the incomplete logs validate against the bundled official SARIF 2.1.0 schema. `SarifReportWriterTest` unchanged and green.
- Compatibility changes: additive, with one fix. `SarifLog.Run`, `Rule`, `Result` and `Region` gained components, and backward-compatible constructors retain the old shapes. `Run` and `Rule` now exclude null fields — without that the new components broke every *existing* SARIF log by emitting {@code fullDescription: null}, which the official schema rejects; the existing `SarifReportWriterTest` caught it immediately.
- Remaining limitations: a check that could not run travels as a notification with the reason code in its properties rather than a SARIF `descriptor`, because a descriptor would have to be a declared rule object and declaring a rule for a check that never ran would be fiction. `relatedLocations` is always emitted as an empty array for findings that have none, which the schema permits but a consumer may render as "no related locations" rather than "none recorded". `detect --format sarif` still renders the legacy antipattern log; only `gate` selects the findings adapter.
