# PRD: Контекстно-зависимые исключения (Smart Exclusions / Ignore List)

## 1. Контекст и проблематика
**Проблема:** В любом Java-проекте есть классы, для которых классические ООП-метрики не применимы. Например, у классов DTO (Data Transfer Object) или `@Entity` всегда низкая связность (Cohesion) и нарушена инкапсуляция, а тестовые классы часто имеют огромный размер и плоскую структуру. Сейчас инструмент анализирует всё подряд, генерируя ложные срабатывания (false positives) и тратя процессорное время на парсинг файлов, результаты которых нам не нужны.
**Цель:** Дать пользователю возможность передать конфигурационный файл с регулярными выражениями (Regex), чтобы исключить определенные пакеты и классы из процесса анализа *еще до этапа расчета метрик*.

## 2. Пользовательские сценарии (Use Cases)

*   **UC-1: Игнорирование служебного кода.** Разработчик настраивает CI-пайплайн. У него в проекте есть пакет `com.myapp.generated.*` (сгенерированный код gRPC) и классы с суффиксом `*Test.java`. Он добавляет файл исключений и передает его в CLI, чтобы тулза вообще не тратила время на эти файлы и не выдавала по ним метрики.
*   **UC-2: Разделение логики (Core vs Web).** Архитектор хочет проверять строгими метриками только слой Domain/Business Logic, полностью игнорируя слой контроллеров (где специфика Spring Framework заставляет писать код определенным образом). Он пишет regex, оставляющий для проверки только пакет `com.myapp.domain.*`.

## 3. Функциональные требования (MVP)

### 3.1. CLI Интерфейс
*   Добавить новый флаг: `--exclude-file=<path>` (алиасы: `-e`, `--ignore`).
*   Если флаг не передан, инструмент анализирует все `.java` файлы в указанной директории (обратная совместимость).

### 3.2. Формат конфигурационного файла
Для удобства разработчиков (по аналогии с `.gitignore` или `.eslintignore`), самым простым и понятным решением для MVP будет обычный текстовый файл (например, `.metrics-ignore` или `exclusions.txt`), где каждая строка — это регулярное выражение.

*Альтернатива:* Использовать JSON/YAML. Для MVP текст проще, но если в будущем мы захотим гибко настраивать (например, "для DTO игнорировать только метрику LCOM, а WMC считать"), то лучше заложить фундамент в YAML.

**Предлагаемый формат для MVP (YAML):** `config.yml`
```yaml
exclusions:
  # Регулярные выражения для полного пути к пакету
  packages:
    - "^com\\.mycompany\\.project\\.generated\\..*"
    - ".*\\.dto$"
  
  # Регулярные выражения для имен классов
  classes:
    - ".*Test$"
    - ".*IT$"          # Интеграционные тесты
    - ".*Entity$"
    - ".*Controller$"
```
*(Примечание: Использование YAML позволяет сделать структуру самодокументируемой и легко расширяемой в будущем).*

### 3.3. Логика фильтрации (Core Logic)
1.  **Раннее отсечение (Early Exit):** Фильтрация должна происходить **ДО** построения AST (Abstract Syntax Tree) и расчета метрик. 
2.  Инструмент сканирует директорию, собирает список `.java` файлов и определяет их полные имена (`com.package.MyClass`).
3.  Каждое полное имя проверяется по регулярным выражениям из файла конфигурации.
4.  Если класс или его пакет совпадает хотя бы с одним Regex — файл отбрасывается и в расчетах не участвует.
5.  В итоговом отчете (и в логах) желательно вывести одной строкой `INFO: Skipped 45 files matching exclusion rules.`.

## 4. Граничные случаи (Edge Cases) для обработки

1.  **Файл указан, но не найден:** Инструмент должен прервать работу с фатальной ошибкой `Error: Exclusions file not found at <path>`, чтобы предотвратить "тихий" прогон по всему коду и падение CI.
2.  **Невалидное регулярное выражение:** При парсинге файла (если пользователь написал кривой Regex, например, незакрытую скобку), инструмент должен упасть при запуске с четким сообщением: `Error parsing regex in <file> on line X: <RegexExceptionDetails>`.
3.  **Пустой файл или пустые списки:** Инструмент просто обрабатывает все файлы, как если бы флага не было (возможно, выдает `WARN: Exclusion file is empty`).

## 5. Разница между Exclusions и Baseline (Для документации)

Разработчикам нужно четко объяснить, когда использовать какой инструмент:
*   **Exclusions (Игнор-лист):** Используем для файлов, которые *в принципе* не нужно проверять архитектурными метриками (тесты, DTO, миграции БД). Улучшает производительность.
*   **Baseline (Линия отсечения):** Используем для файлов бизнес-логики (Core, Services), которые *нужно* проверять, но они уже написаны плохо (легаси). Мы хотим отслеживать их, чтобы они не стали еще хуже.

## 6. Метрики успеха
*   **Техническая:** Бенчмарк (на твоих 289 665 строках). Если мы через regex исключим 30% файлов (тесты и DTO), время выполнения должно сократиться пропорционально (например, со 137 секунд до ~95 секунд).
*   **Продуктовая:** Резкое снижение false positives при анализе стандартных Spring Boot / Jakarta EE приложений.

## 7. Вне рамок MVP (Future Scope / На вырост)
*Это важно зафиксировать, чтобы понимать, куда фича может развиваться дальше:*
*   **Профили метрик (настоящие Context-Dependent Profiles):** Вместо полного игнорирования, в будущем можно будет задавать в этом файле разные пороги. Например: *«Для классов `*Controller` лимит CBO (Coupling) = 20, а для `*Service` лимит CBO = 10»*.
*   **Игнорирование по аннотациям:** Автоматически отбрасывать файлы, если внутри есть `@Entity`, `@Data` (Lombok) или пользовательская `@SuppressWarnings("architecture")`. (Это потребует построения AST, поэтому будет медленнее, чем Regex по имени файла).
