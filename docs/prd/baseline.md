# PRD: Механизм Baseline (Линия отсечения)

## 1. Контекст и проблематика
**Проблема:** При внедрении нашего инструмента в существующие (легаси) проекты, он выявляет сотни или тысячи архитектурных нарушений (выходов за эталонные интервалы 50+ ООП-метрик). Это вызывает "alert fatigue" (усталость от алертов). Разработчики не могут исправить всё сразу, поэтому CI-пайплайн будет постоянно красным. Как итог — инструмент удаляют или игнорируют.
**Цель:** Позволить командам зафиксировать текущее состояние проекта как «базовое» (Baseline). Инструмент должен игнорировать старые нарушения и сигнализировать **только о новых** архитектурных деградациях или ухудшении старых.

## 2. Пользовательские сценарии (Use Cases)

*   **UC-1: Инициализация.** Tech Lead запускает CLI локально с флагом генерации. Инструмент анализирует проект и создает файл `baseline.json`, записывая туда все текущие метрики, выходящие за пределы нормы. Файл коммитится в Git.
*   **UC-2: Ежедневная работа в CI (Защита).** В GitHub Actions CLI запускается с флагом чтения бейзлайна. Разработчик Вася добавляет новый God Object. Инструмент сравнивает метрики Васиного кода с `baseline.json`, видит новое нарушение, возвращает `exit code 1` и роняет сборку.
*   **UC-3: Рефакторинг (Эффект храповика).** Разработчик Петя рефакторит старый класс, снижая его связность (CBO) с 20 (в baseline) до 10. CI проходит успешно. В идеале Петя (или автоматика) обновляет `baseline.json`, чтобы зафиксировать новый, улучшенный стандарт.

## 3. Функциональные требования (MVP)

### 3.1. Генерация Baseline-файла
*   **CLI интерфейс:** Добавление флага `--generate-baseline` (или `-g`) и опционального флага `--baseline-file=<path>` (по умолчанию `baseline.json` в корне).
*   **Логика:** При вызове флага инструмент рассчитывает метрики, находит все выходы за эталонные интервалы, формирует структуру данных и сохраняет ее в JSON.
*   **Что сохраняем в файл (Важно!):**
    *   Нельзя привязываться к номерам строк кода (они меняются при добавлении пустой строки или комментария).
    *   Привязка должна быть к **сигнатуре сущности**: `Пакет -> Класс -> [Метод]`.
    *   Сохраняем только *нарушенные* метрики и их текущие (базовые) значения.

### 3.2. Применение Baseline-файла (Режим проверки)
*   **CLI интерфейс:** Добавление флага `--baseline=<path>` (или `-b`).
*   **Логика работы:**
    1. Инструмент парсит проект и считает актуальные метрики.
    2. Сравнивает актуальные нарушения с `baseline.json`.
    3. **Правила фильтрации (Core Logic):**
        *   Если нарушение есть в проекте, но **отсутствует** в baseline -> `АЛЕРТ (Новый техдолг)`.
        *   Если нарушение есть в baseline, и актуальное значение **стало хуже** (еще дальше от эталонного интервала) -> `АЛЕРТ (Деградация)`.
        *   Если нарушение есть в baseline, и актуальное значение **такое же** -> `ИГНОР (Прощаем старый грех)`.
        *   Если нарушение есть в baseline, а актуальное значение **стало лучше** (или вообще вошло в норму) -> `ИГНОР (Хвалим, опционально выводим INFO сообщение "Обновите baseline")`.

## 4. Технический дизайн (Формат файла)

Файл должен быть легко читаемым (для code review) и удобным для парсинга. Предлагаемый формат `baseline.json`:

```json
{
  "version": "1.0",
  "generatedAt": "2023-10-27T10:00:00Z",
  "violations": {
    "com.project.services.PaymentService": {
      "WMC": {
        "currentValue": 55,
        "threshold": 30,
        "description": "Weighted Method Count exceeds threshold"
      },
      "CBO": {
        "currentValue": 18,
        "threshold": 10
      }
    },
    "com.project.models.User.calculateDiscount()": {
      "LCOM4": {
        "currentValue": 0.9,
        "threshold": 0.5
      }
    }
  }
}
```
*Примечание: Использование полных имен классов/методов (FQDN) решает проблему сдвига строк кода.*

## 5. Граничные случаи (Edge Cases) для обработки

1.  **Переименование класса/метода:** В рамках MVP, если класс переименовали, инструмент будет считать его новым классом. Старая запись в baseline станет "сиротой", а на переименованный класс вылетит алерт, если он нарушает эталон. *Решение для MVP: Это нормальное поведение. Разработчик должен либо исправить архитектуру переименованного класса, либо перегенерировать baseline.*
2.  **Отсутствие файла baseline при указанном флаге `--baseline`:** Инструмент должен падать с понятной ошибкой: `Error: Baseline file not found at path <...>. Run with --generate-baseline first.`
3.  **Удаление класса с нарушениями:** Если класс удален, его запись в baseline просто игнорируется при проверке.

## 6. Метрики успеха (Success Metrics) для фичи

*   **Технические:** Время загрузки и парсинга `baseline.json` в проекте на 300k строк не должно превышать 1-2 секунд (не должно аффектить общий бенчмарк в 2:17 мин).
*   **Продуктовые (после Open Source релиза):**
    *   Процент запусков CLI с флагом `--baseline` (ожидаем >70% в CI окружениях).
    *   Снижение количества жалоб на "слишком много предупреждений" в Issues на GitHub.

## 7. Вне рамок MVP (Out of Scope)
*То, что мы НЕ делаем сейчас, чтобы сэкономить время разработки:*
*   Автоматическое обновление (перезапись) baseline в CI пайплайне при улучшении метрик (пока что разработчики должны делать это вручную через `--generate-baseline`).
*   Сложный fuzzy-matching при переименовании методов.
*   Распределенное хранение baseline (пока просто файлик в репозитории проекта).

---

### Твои следующие шаги как разработчика:
1.  **Архитектура ядра:** Убедиться, что твой движок расчета метрик умеет выплевывать результаты не сразу в консоль, а в промежуточную Data Class / POJO структуру, которую можно прогнать через слой фильтрации.
2.  **Реализация слоя сравнения:** Написать логику `BaselineFilter`, который берет сырые нарушения и отсекает те, что покрыты файлом.
3.  **Тесты:** Обязательно написать Unit-тест на логику "деградации" (когда базовое значение было 50, стало 55 -> должен быть сгенерирован алерт).
