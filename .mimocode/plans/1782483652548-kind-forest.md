# Plan: Baseline Mechanism Implementation

## Context

The PRD describes a mechanism to combat "alert fatigue" in legacy projects. When teams adopt the metrics tool on large codebases, hundreds/thousands of violations are found. The baseline feature allows teams to snapshot current violations, commit the snapshot to Git, and only alert on **new or worsened** violations in CI.

## Approach

**Add flags to the existing `validate` command.** The `validate` command already does threshold-based comparison — baseline is a natural extension. This keeps the CLI surface minimal.

New flags on `validate`:
- `--generate-baseline=<path>` — generate baseline.json instead of normal validation output
- `--baseline=<path>` — check against an existing baseline (filter violations)

When neither flag is present, `validate` works exactly as before (no breaking change).

## New Files

### 1. `BaselineEntry.java` — Data model for a single baseline violation
**Path:** `java-metrics-cli/src/main/java/org/b333vv/metric/cli/BaselineEntry.java`

```java
record BaselineEntry(
    String metricCode,      // e.g. "WMC"
    double currentValue,    // violation value at snapshot time
    double minThreshold,    // from thresholds.json
    double maxThreshold     // from thresholds.json
)
```

### 2. `BaselineFile.java` — Data model + JSON serialization for baseline.json
**Path:** `java-metrics-cli/src/main/java/org/b333vv/metric/cli/BaselineFile.java`

JSON structure (per PRD):
```json
{
  "version": "1.0",
  "generatedAt": "2023-10-27T10:00:00Z",
  "violations": {
    "com.project.services.PaymentService": [
      { "metricCode": "WMC", "currentValue": 55, "minThreshold": 0, "maxThreshold": 30 }
    ],
    "com.project.services.PaymentService.calculateDiscount()": [
      { "metricCode": "LCOM", "currentValue": 0.9, "minThreshold": 0, "maxThreshold": 0.5 }
    ]
  }
}
```

Entity key format:
- Class-level: `com.project.services.PaymentService` (from `ClassReport.qualifiedName()`)
- Method-level: `com.project.services.PaymentService.calculateDiscount()` (class QN + `.` + `MethodReport.signature()`)

### 3. `BaselineFilter.java` — Core comparison logic
**Path:** `java-metrics-cli/src/main/java/org/b333vv/metric/cli/BaselineFilter.java`

Method: `BaselineResult compare(MetricReport report, Map<String,Threshold> thresholds, BaselineFile baseline)`

**Violation detection** (reuses `ValidateCommand` logic):
- For each class/method metric, check if value exceeds thresholds (min/max bounds).

**Comparison logic** (the core of the feature):

| Condition | Result | Exit code impact |
|---|---|---|
| Violation exists now but **not** in baseline | **NEW_VIOLATION** (alert) | Yes |
| Violation in baseline, current value **further** from threshold | **DEGRADED** (alert) | Yes |
| Violation in baseline, current value **same** | **UNCHANGED** (ignore) | No |
| Violation in baseline, current value **closer** to threshold or back in range | **IMPROVED** (info) | No |
| Violation in baseline, no longer violating | **RESOLVED** (info) | No |

**Distance calculation** for "worse/better":
- For metrics where max is the bound: `distance = value - maxThreshold` (positive = violating)
- For metrics where min is the bound: `distance = minThreshold - value` (positive = violating)
- Larger positive distance = worse. Negative distance = within threshold = resolved.

### 4. `BaselineCheckResult.java` — Output model for check results
**Path:** `java-metrics-cli/src/main/java/org/b333vv/metric/cli/BaselineCheckResult.java`

```java
record BaselineCheckResult(
    String status,                              // "PASSED" | "FAILED"
    int newViolations,
    int degradedViolations,
    int unchanged,
    int improved,
    int resolved,
    List<ViolationDetail> alerts                // new + degraded only
)
```

## Modified Files

### 1. `ValidateCommand.java`
Add three new flags:
```java
@CommandLine.Option(names = "--generate-baseline", paramLabel = "PATH",
        description = "Generate baseline.json with current violations.")
private Path generateBaselinePath;

@CommandLine.Option(names = "--baseline", paramLabel = "PATH",
        description = "Check against existing baseline (only alert on new/degraded violations).")
private Path baselinePath;
```

Modify `call()` method:
- If `--generate-baseline` is set: analyze → find all violations against thresholds → write baseline.json → return 0
- If `--baseline` is set: analyze → find violations → load baseline → filter → write report → exit code 1 if new/degraded
- If neither: existing behavior (unchanged)

Extract shared threshold loading into a static helper method (currently `loadThresholds()` is private instance method).

## Key Design Decisions

1. **Entity key = FQDN (class) or FQDN.signature (method)** — matches PRD requirement to avoid line-number dependency
2. **Distance-based comparison** — more meaningful than simple "value changed"; captures severity of degradation
3. **Thresholds required for both generate and check** — ensures consistent violation detection
4. **Array of entries per entity** — an entity can violate multiple metrics simultaneously
5. **No breaking changes** — existing `validate` behavior preserved when new flags are absent
